## 4. Shared Implementation Principles

1. **No direct state editing**: managed-project `progress.md` and `progress-history.md` are only mutated by `progress.py`.
2. **Doc status owner**: doc frontmatter `status` is only mutated by `status_transition.py` or the owning orchestration flow already defined by references for specific non-status fields.
3. **No Python `eval`**: required-artifacts condition DSL must use a whitelist parser.
4. **Atomic writes**: every mutating script writes via backup + temporary file + atomic rename; multi-file operations roll back on failure.
5. **Idempotent retries**: safe repeats should no-op or append explicit idempotent history where references allow it.
6. **Exit code contract**: success exits 0; validation or state-machine rejection exits non-zero with actionable stderr.
7. **Current repo is not a managed project**: scripts and tests must operate on explicit target roots / temp fixtures, not treat `dev-workflow-skills2` itself as workflow-managed.

## 6. Gap-3 / Gap-4 / Gap-5 Detailed Plan

### 6.1 Gap-3 — Verification Fail Rollback

Add legal task transition:

| From | To | Trigger | Required Check |
|------|----|---------|----------------|
| `verifying` | `code-revising` | `development-code-write` verification retry | `verification_result.md` exists and frontmatter `verification_status in {fail, partial}` |

Rejected behavior:

- Do not allow `verifying -> verified` unless `verification_status=pass`.
- Do not invoke bug-triage for Stage 4 verification fail.
- Do not hand-edit `progress.md`.

### 6.2 Gap-4 — Development Bug Flow Task Rollback

When `bug-start --root-cause development` or `bug-rework` routes to Development, parse the active BUG body:

- Required section: `## Triage Analysis`
- Required line: `**Affected Task(s)**: T1, T3` or explicit `unable to localize`
- Current source of truth: BUG body, not frontmatter

Rollback table:

| Current Task State | Target State | Required Classification |
|--------------------|--------------|-------------------------|
| `verified` | `test-revising` | affected task, test-only/test-first fix required |
| `verified` | `code-revising` | affected task, source-code fix required |
| `code-review-passed` | `code-revising` | affected task, source-code fix needed before verification |

Classification strategy for MVP:

1. If BUG body clearly contains test-only/test-first language in Triage Analysis or affected module detail, route `verified -> test-revising`.
2. If BUG body clearly contains source-code fix language or source file paths, route `verified|code-review-passed -> code-revising`.
3. If `Affected Task(s)` is present but classification is ambiguous (no test-only/source-code language match), leave each affected task state unchanged. The standard `bug-start` / `bug-rework` mutation still routes `current_stage` to `development` and `sub_state` to `write`; no extra stage edit is required. Append a history entry stating that `development-planning-write` must replan/route. Do not guess.
4. If `Affected Task(s)` is absent and no replan path is selected, reject with human escalation message.

### 6.3 Gap-5 — Active Bug Flow Retest Rework

Add command:

```bash
skills/workflow-protocol/scripts/progress.py bug-rework --bug <BUG-NNN.md>
```

Preconditions:

- `bug_flow.active == true`
- `current_stage == testing`
- `sub_state == review-passed`
- latest `docs/release{release}/testing/report.md` frontmatter `verification_status in {fail, partial}`
- `<BUG>` path equals `progress.md bug_flow.bug_report_path`
- BUG frontmatter `root_cause == progress.md bug_flow.root_cause`
- root cause is one of `srs`, `architecture`, `development`

Mutation:

1. Keep `bug_flow.active: true`.
2. Keep `bug_flow.bug_report_path` and `bug_flow.root_cause` unchanged.
3. Set `current_stage` back to root-cause stage:
   - `srs -> srs-specification`
   - `architecture -> architecture-design`
   - `development -> development`
4. Set `sub_state: review-passed -> write`.
5. Set `review_iteration: 0`.
6. Append history event `bug-rework`. **Phase 6.2 implementation note (supersedes the original plan wording)**: the canonical replay-token contract requires the summary to carry `bug=<path> root_cause=<srs|architecture|development> Bug Flow rerouted [rollback=Tn:old->new;...]`; the test-report path is a forward CLI precondition (latest `docs/release<x.y>/testing/report.md` shows `verification_status in {fail, partial}`) and is **not** recorded in the history entry, since replay never re-reads test-reports. See `command-reference.md` §9 Append history for the exact template.
7. If root cause is development, reuse Gap-4 rollback logic.

Rejected behavior:

- Do not call `bug-start` again for the same active issue.
- Do not create a second BUG for retest fail/partial.
- Do not call `bug-close` unless retest passed.
- Do not hand-edit `current_stage` or bug_flow fields.

- `triggered_by_bug` must be a BUG ID like `BUG-007`, not a path.

## 8. changelog.py Plan

### 8.1 Incremental Doc Types

Require `## Pending Changes` and `## Change Log`:

- `prd`, `architecture`, `retrospective`
- `srs`, `acceptance-plan`, `integration-plan`, `architecture-delta`
- `development-plan`, `task-breakdown`, `detailed-design`
- `cr`, `bug-report`, `workflow-incident`

Snapshot docs do not require Change Log:

- `test-preparation`, `test-procedure`, `test-report`
- `deployment-doc`, `operation-manual`, `installation-result`
- `test-review-report`, `code-review-report`, `verification-result`
- `source-system-analysis` types

### 8.2 promote

Algorithm:

1. Load frontmatter + Markdown body.
2. If doc type is not incremental, exit 0 if sections are absent; validate any present sections if present.
3. Extract `## Pending Changes` and `## Change Log`.
4. Reject if required sections are missing.
5. Parse pending entries using strict regex:
   - `- YYYY-MM-DDTHH:MM:SSZ [Section X[.Y]|frontmatter|全文]: summary`
6. Merge entries into Change Log grouped by `### YYYY-MM-DD`.
7. Sort date groups descending; sort entries inside a date ascending.
8. Clear Pending Changes body.
9. Atomic write and self-validate.

### 8.3 validate

Checks:

- Required sections exist for incremental docs.
- Pending Changes is empty except blank lines and HTML comments.
- Change Log group headings are valid dates.
- Change Log entries match strict entry regex.
- Timestamps inside one date group are monotonic ascending.

## 9. status_transition.py Plan

### 9.1 CLI Interface

Recommended MVP interface:

```bash
skills/doc-guardian/scripts/status_transition.py apply \
  --event <write-complete|review-issues|review-passed|human-confirmed> \
  --doc <path> [--doc <path> ...]

skills/doc-guardian/scripts/status_transition.py apply \
  --event <event> \
  --stage-current

skills/doc-guardian/scripts/status_transition.py apply \
  --event <event> \
  --task <Tn> \
  --doc <path> [--doc <path> ...]

skills/doc-guardian/scripts/status_transition.py plan \
  --event <event> \
  --doc <path> [--doc <path> ...]
```

`plan` is dry-run and prints intended old/new statuses without mutation.

### 9.2 Event Mapping

| Event | Allowed Old Status | New Status | Notes |
|-------|--------------------|------------|-------|
| `write-complete` | `draft`, `revising` | `in-review` | Called after `progress.py update --event write-complete` succeeds. |
| `review-issues` | `in-review` | `revising` | Called after review reports issues and progress event succeeds. |
| `review-passed` | `in-review` | `review-passed` | Called after progress event succeeds. |
| `human-confirmed` | `review-passed` | `approved` | Only gated docs: PRD/SRS/Architecture/CR. |

No-op rule: if a doc is already at the target status, return success and do not duplicate Change Log entries unless `--record-idempotent` is later added.

### 9.3 Change Log Atomicity

For incremental docs:

1. Load file and compute new frontmatter `status` + `updated` timestamp.
2. Add a Pending Changes entry: `- <now> [frontmatter]: 更新 status 至 <new-status>`.
3. Promote in memory using changelog logic.
4. Validate in memory / temp output.
5. Atomic write.

For snapshot docs:

- Update frontmatter `status` + `updated`; do not require Pending/Change Log.

Multi-doc transaction:

1. Pre-validate all docs and planned transitions.
2. Write each doc with backup.
3. If any write or validation fails, restore all touched docs.
4. Exit non-zero with per-doc failure details.

### 9.4 Caller Sequencing

Required sequence for stage skills:

1. Owning write/review skill creates or edits doc body/frontmatter fields it owns.
2. Owning skill runs `changelog.py promote` if incremental.
3. Owning skill runs `validate.py file`.
4. Owning skill calls `progress.py update --event <event>`.
5. If progress event succeeds, caller immediately calls `status_transition.py apply --event <event> ...`.
6. Caller reruns `validate.py file` or `validate.py consistency` before advance.

Reason for progress-first ordering: current SKILL.md batches explicitly state helper runs after successful `progress.py update --event`. Helper idempotency handles retry if step 5 fails.

## 10. Required Artifacts and Condition DSL

### 10.1 Resolver Inputs

- `progress.md` fields: `scenario`, `scenario_subtype`, `current_stage`, `release`, `development_state.task_states`.
- SRS frontmatter fields: `is_multi_module`, `architecture_change`; default false only when SRS is unavailable for condition evaluation, as references state.
- Optional `task_id` for per-task artifact rendering.

### 10.2 DSL Parser

Implement recursive descent parser for:

- Operators: `==`, `!=`, `&&`, `||`, parentheses.
- Variables: only `scenario`, `scenario_subtype`, `current_stage`, `release`, `srs.is_multi_module`, `srs.architecture_change`.
- Literals: bools, quoted strings, whitelisted enum literals.
- Reject function calls, unknown variables, unknown enum literals, assignment `=`, and property chains longer than 2.

Required parser tests:

1. `scenario == S3`
2. `srs.is_multi_module == true`
3. `(scenario == S2) && (current_stage == srs-specification)`
4. `srs.unknown_field == true` rejects
5. `is_admin(scenario)` rejects
6. `current_stage == not-a-stage` rejects

## 11. Atomicity and Rollback Strategy

### 11.1 progress.py

All mutating commands follow:

1. Load current `progress.md` and `progress-history.md`.
2. Acquire `.progress.lock`.
3. Re-read current files after lock to avoid stale state.
4. Compute new progress and history entry.
5. Validate transition and command-specific preconditions.
6. Write history append and progress overwrite using temp files.
7. Run consistency replay check where feasible.
8. On failure, restore backed-up files.
9. Release lock.

### 11.2 BUG Frontmatter Multi-file Mutations

`release-start` mutates `progress.md`, `progress-history.md`, and multiple BUG docs. It must:

1. Pre-validate all BUG docs.
2. Compute all BUG frontmatter updates.
3. Write BUG docs with backups.
4. Write progress/history.
5. Run validation.
6. Roll back BUG docs and progress/history on any failure.

### 11.3 status_transition.py

Multi-doc status changes follow all-or-nothing rollback. This protects stages with multiple artifacts, e.g. SRS + Acceptance Plan + Integration Plan.

   - code-writing -> code-review -> code-review-passed
   - verifying -> verified

3. **Gap-3 Verification Fail**
   - task in verifying
   - verification_result fail

   - `update --task T1 --status code-revising` succeeds

4. **Gap-4 Development Bug Rollback**
   - testing fail creates BUG with `root_cause=development`
   - BUG body has `Affected Task(s): T1`

   - ambiguous BUG requires planning route and does not guess

5. **Gap-5 Retest Rework**
   - active Bug Flow returns to testing
   - test-report fail/partial
   - second `bug-start` rejects
   - `bug-rework` reroutes to same root-cause stage

6. **Incident Path**
   - BUG root_cause prd-exception
   - incident skeleton valid
   - `incident-start`
   - `incident-resolve continue` clears bug_flow and returns testing/review-passed
   - `incident-resolve abort|reconstruct` terminal cleanup

7. **Release-start Consumes Bugs**
   - closed release with unresolved BUGs
   - `release-start` sets BUG `target_release` and `consumed_in_release`
   - duplicate consumption rejected by validation
